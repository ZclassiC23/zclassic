# ISA audit — is SHA-256 the only accelerated path compiled out?

**Scope:** every accelerated path in `lib/crypto/` and `lib/sapling/`.
**Question:** does the shipped build actually contain, and actually reach, the
vector/ISA code we believe we ship?

**Answer: no, SHA-256 was not the only one. Two paths were compiled out of every
shipped binary, and one dispatch predicate was computed and then discarded.**

---

## 0. The shipped flags — what the compiler defines

`Makefile:409` — `CFLAGS = ... $(if $(ZCL_NATIVE),-march=native,-march=x86-64-v3) ...`.
No per-object `-march` / `-msha` / `-mavx512*` / `-madx` override exists anywhere
in the Makefile, so this applies uniformly to every `.c` in the tree.

```
$ gcc -march=x86-64-v3 -dM -E - </dev/null | grep -E '__(SHA|AVX|BMI|ADX)…'
```

| macro | defined at `-march=x86-64-v3`? |
|---|---|
| `__AVX__`, `__AVX2__` | **yes** |
| `__BMI__`, `__BMI2__` | **yes** |
| `__FMA__`, `__F16C__`, `__LZCNT__`, `__MOVBE__`, `__POPCNT__`, `__SSE*__`, `__SSSE3__`, `__XSAVE__` | **yes** |
| `__SHA__` | **NO** |
| `__AVX512F__` (and every other `__AVX512*__`) | **NO** |
| `__ADX__` | **NO** |
| `__AES__`, `__PCLMUL__`, `__VAES__`, `__GFNI__` | **NO** |

The host (`AMD Ryzen 9 7950X3D`, Zen 4) reports `sha_ni avx512f avx512vl avx512dq
avx512ifma avx512bw avx512cd bmi2 adx` in `/proc/cpuinfo`. **Every** macro in the
"NO" column corresponds to an instruction set the CPU physically has.

So the rule is: any `#ifdef __<ISA>__` where `<ISA>` is in the NO column deletes
that code from the shipped binary. Any bare `__attribute__((target(...)))` +
runtime `__builtin_cpu_supports` / CPUID does **not** — it compiles in and
dispatches at run time. That is the whole defect class.

## 2. DEFECT FIXED — `sha3_avx512.c` was compiled out of every shipped binary

**What was wrong.** The entire AVX-512 4-way body sat behind `#ifdef __AVX512F__`.
`-march=x86-64-v3` never defines it, so `sha3_512_x4()` in every binary we ship
was the `#else` branch: four sequential scalar SHA3-512 hashes. Same shape as the
SHA-256 defect, same cause, same silence.

**Blast radius.** `sha3_512_x4()` has two production call sites, both in the
file-transfer frame cipher: `lib/net/src/file_service.c:169` (encrypt) and `:228`
(decrypt). One 64 KiB frame = 256 calls. Not consensus crypto — but it *is*
wire-visible, so a divergence between two builds would break file-market
interop, not the chain.

**It had never been compiled, not once.** Under `-mavx512f` the absorb loop
raises `-Warray-bounds`: it declared `uint64_t lanes[4]` (32 bytes) and then
`_mm512_loadu_si512(lanes)` read the full 64-byte register — a 32-byte
out-of-bounds read. The repo builds `-Wall -Wextra -Werror`, so had the guard
ever been satisfied the build would have failed. (The upper 4 slots were never
squeezed, so the garbage did not reach the output — but it was UB, and it is
proof the code was dead.)

**The fix** (same shape as job 2.1, and as the known-good files in rows 3–5):

- Vector lane now carries `__attribute__((target("avx512f")))` — it compiles
  into the `-march=x86-64-v3` baseline.
- Entered only after `sha3_keccakf_avx512_available()` confirms CPUID **and** OS
  (XCR0) support — reusing the already-tested predicate from `keccak_avx512.c`.
- Staging array widened to `uint64_t lanes[8] = {0}`; the OOB read is gone.
- Scalar lane kept as the always-available fallback **and** the oracle reference.
- Added `sha3_512_x4_select_impl()` (mirrors `sha3_256_x4_select_impl`) so the
  parity oracle and bench can force either lane.
- Default ON (`SHA3_512_X4_AVX512_DEFAULT_ENABLED 1`) — unlike row 3, this
  geometry is lane-parallel with no cross-lane gather, and it measures a win.

**Byte identity — proven, not assumed.** New test group `sha3_512_x4`
(`lib/test/src/test_sha3_512_x4.c`) is a three-way differential oracle: an
independent restatement of the contract (four one-shot `sha3_512` calls over the
72-byte preimage) vs the scalar lane vs the AVX-512 lane, over 20 000 random
`(key, nonce, counter)` triples, plus counter-carry/wrap boundaries
(2^8 / 2^16 / 2^32 / 2^64−1), plus teeth.

Local three-way run against the edited production file, 200 000 triples,
`-march=x86-64-v3`:

```
avx512 available: yes        AUTO installs: AVX512
scalar vs contract : 0 mismatches / 200000
avx512 vs contract : 0 mismatches / 200000
avx512 vs scalar   : 0 mismatches / 200000
teeth scalar: PASS           teeth avx512: PASS
```

**Teeth** (a benchmark of a hollow function is worse than no benchmark) — on
*both* lanes: keystream is non-zero; the four lanes differ from each other (not
one hash memcpy'd four times); a one-bit flip in the key, a one-bit flip in the
nonce, and `counter+1` each change the output.

Byte identity is also the whole rollout-safety argument: because the vector lane
emits exactly the bytes the scalar lane emits, a node on this build and a node
still on the old scalar-only build exchange file-market frames unchanged. There
is no flag day and no version negotiation, because there is no difference to
negotiate.

**Before/after** (same binary, same host, 3000 × 64 KiB frames, forced lanes):

| lane | ns/call (256 B keystream) | MiB/s | µs per 64 KiB frame |
|---|---|---|---|
| scalar-x4 (**what we shipped**) | **1816.1** | 134.4 | 464.9 |
| avx512-4way (**what we now ship**) | **1051.8** | 232.1 | 269.3 |
| | **1.73x** | | −195.6 µs/frame |

## 3. DEFECT FIXED — a dispatch predicate computed and then discarded (`fr_avx512.c`)

`detect_cpu_features()` computes `cpu_has_avx512ifma` (`fr_avx512.c:49-63` —
CPUID leaf-7 EBX bit 21, plus an AVX512F check and an XCR0 OS check).
`init_dispatch()` **never reads it**
— there is no VPMADD52 implementation anywhere in the file. The only consumer
was `fr_accel_implementation()`, which returned:

```c
if (cpu_has_avx512ifma) return "AVX-512 IFMA (VPMADD52 + MULX+ADCX+ADOX)";
```

`config/src/boot.c:683` prints that on every boot. On this host — which *does*
have `avx512ifma` — the node has been booting with `Field arithmetic: AVX-512
IFMA (VPMADD52 + MULX+ADCX+ADOX)` while executing the BMI2 path. A tier that has
never executed was being reported as the running one.

This is exactly the mechanism by which the SHA-256 defect stayed invisible: the
thing that was supposed to tell an operator which path is live was reporting a
capability instead of a dispatch.

**Fix (reporting only — no arithmetic touched):** report what `init_dispatch()`
actually installs, and surface IFMA as detected-but-unimplemented so the headroom
stays visible rather than being laundered into a false claim:

```
"BMI2 MULX (AVX-512 IFMA present, unimplemented)"   /* was: "AVX-512 IFMA (…)" */
"BMI2 MULX"
"portable (__int128)"
```

ADX is no longer claimed either — see §4.2. The file-header tier list was
corrected to match. Nothing asserts on the old string (checked).

## 4. Reported, not fixed

### 4.1 `blake2b_avx2.c` detection has no XCR0 / OS check

`detect_features()` (`blake2b_avx2.c:30`) reads CPUID leaf-7 EBX bits 5 and 16
and nothing else. Every other ZMM entry in the tree additionally checks
XGETBV/XCR0 bits 5,6,7 first — `keccak_avx512.c`, `sha3_256_x4.c` and (now)
`sha3_avx512.c` all go through `sha3_keccakf_avx512_available()`, and even
`fr_avx512.c:56-63`, which has no ZMM path at all, gates its IFMA flag on XCR0.
CPUID reports what the *silicon* has; XCR0 reports what the *OS* has enabled.
On a kernel booted with AVX-512 state disabled, `g_has_avx512f` would read 1 and
`blake2b_compress_8way` would `SIGILL`.

Practically unreachable on any supported Linux, and it is not a compiled-out
path — but it is the one place where a live dispatch predicate is weaker than
the house pattern, and it sits on the Equihash verification path. Fixing it
means changing detection on a consensus-adjacent path, which deserves its own
job and its own gate. **Not touched.**

### 4.2 The BMI2/ADX field multiply never builds a carry chain — CONFIRMED

The brief asked this be verified properly rather than assumed. It is true, and
slightly worse than described.

`fp_mont_mul_bmi2` (`lib/sapling/src/fr_avx512.c:189`, the 6-limb Fp multiply)
— **every** `_addcarryx_u64` in both the multiply loop and the reduction loop
takes a literal `0` carry-in:

```c
for (int j = 0; j < 6; j++) {
    uint64_t lo = _mulx_u64(a[j], b[i], &hi);
    cf  = _addcarryx_u64(0, t[j], lo,        (unsigned long long *)&t[j]);
    cf2 = _addcarryx_u64(0, t[j], carry_mul, (unsigned long long *)&t[j]);
    carry_mul = hi + cf + cf2;          /* carry folded by a scalar add */
}
```

The carry is extracted to a `char` and folded back with an ordinary addition, so
**zero** carry chains are built — let alone the two independent ones (ADCX on CF,
ADOX on OF) that are the entire reason ADX exists. The `target("bmi2,adx")`
attribute buys MULX and nothing else; `-madx` could be dropped with no codegen
change to this function.

`fr_mont_mul_bmi2` (`:97`, the 4-limb Fr multiply) is marginally better: it
threads `cf` through the `lo` additions (one chain), but the `carry_mul`
additions still use a literal `0`. One chain is what plain `ADC` already gives —
still no dual-chain interleave.

Per the brief: **reported, not fixed.** The measured ceiling is small and job 2.2
has the bigger win. Note that any fix here is Fp/Fr Montgomery arithmetic on the
BLS12-381 pairing path — frozen-consensus-adjacent, and it must clear
`make check-groth16-parity` on a full frozen corpus before it goes anywhere.

### 4.3 `bn254_accel.c` makes the same ADX naming overclaim

`:19` — *"Tier 1: BMI2+ADX — MULX + dual ADCX/ADOX carry chains"* — and `:233`
returns `"BMI2+ADX (MULX+ADCX+ADOX)"`. `bn_fq_mont_mul_bmi2` threads one `cf`
chain through the `lo` adds and uses a literal `0` carry-in for the `carry_mul`
adds, exactly like `fr_mont_mul_bmi2`. No dual chain. This is a naming/comment
inaccuracy, not a compiled-out path or a discarded predicate, and the file is
otherwise the cleanest example of the correct shape in the tree. **Not touched**
— it is arguably job 2.2's territory.

path as if it were our real speed.

`tools/crypto_perf_baseline.csv` and `docs/CRYPTO_PERF.md` were **not** touched:
`sha3_512_x4` is not a `-bench-crypto-vs-rust` primitive, so it owns no row, and
loosening someone else's ratchet ceiling by a careless merge there is precisely
what the shared-file rule exists to prevent.
